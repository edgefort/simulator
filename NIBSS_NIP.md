# NIBSS NIP implementation scope

Provider id: `nibss-nip`.

The module serves the NIP messages 010 through 023 over two transports:

- the **NIP v9.5 SOAP web service** with NIBSS Security Module (SSM) message encryption, which is the production contract (`/NIPWS/...`);
- the earlier **v9.4 XML routes** (`/nip/v9.4/...`), plain XML over local HTTP, kept unchanged for existing consumers.

It also plays NIBSS towards a connected institution (the **inward** flow) through the admin API.

## Sources

- NIP technical specification v9.5 (`NIP Technical Specification Document ver 9 5 .pdf`): message XML formats, field descriptions, section 6 method exposure, section 12 security.
- NIP technical specification v9.4 text (16 June 2017), the original source of messages 010 through 023.
- NIBSS onboarding kit (cited by file name; no kit file is stored in this repository):
  - `MAIL.txt`: outward endpoint paths `/NIPWS/NIPInterface?wsdl` (name enquiry, FT credit) and `/NIPWS/NIPTSQInterface?wsdl` (TSQ), and the key exchange (each side shares its public key).
  - `NIP client test.postman_collection.json`: the request envelope and `/NIPWS/NIPNEInterface` for name enquiry.
  - `FT Credit Implementation in Steps.txt`: the inward credit and status-query sequence.
  - `HOW TO GENERATE KEYS WITH SSM - JAVA.txt` and `SSecurityModule.jar` (class `nfp.ssm.core.SSMLib`, read as bytecode): the SSM payload format and key handling.
- An institution inward WSDL generated by JAX-WS RI (`NIPInward-Dev.wsdl`): document/literal binding, `soapAction=""` on every operation, and an institution-specific target namespace. It is evidence for the inward defaults only; it is not a NIBSS WSDL.

No third-party NIP examples were used to fill missing contract details.

## SOAP web service (v9.5)

### Endpoints

| Path | Source | Methods accepted |
|---|---|---|
| `POST /NIPWS/NIPInterface` | `MAIL.txt` (name enquiry and FT credit) | every method below |
| `POST /NIPWS/NIPTSQInterface` | `MAIL.txt` (TSQ) | every method below |
| `POST /NIPWS/NIPNEInterface` | Postman sample (name enquiry) | every method below |
| `GET {path}?wsdl` | `MAIL.txt` | WSDL of the service at that path |

Each path dispatches on the local name of the SOAP body element, so a client may use the path NIBSS advised for each method. When `simulator.providers.nibss-nip.base-path` is set (for example `/nibss`), the service is served under that prefix (`/nibss/NIPWS/...`) and nowhere else.

### Methods

| Method | Request / response message | Exposed by NIBSS (section 6) |
|---|---|---|
| `nameenquirysingleitem` | 010 `NESingleRequest` / 011 `NESingleResponse` | yes |
| `fundtransfersingleitem_dc` | 012 `FTSingleCreditRequest` / 013 `FTSingleCreditResponse` | yes |
| `txnstatusquerysingleitem` | 016 `TSQuerySingleRequest` / 017 `TSQuerySingleResponse` | yes |
| `fundtransfersingleitem_dd` | 014 `FTSingleDebitRequest` / 015 `FTSingleDebitResponse` | no (institution-side) |
| `balanceenquiry` | 018 `BalanceEnquiryRequest` / 019 `BalanceEnquiryResponse` | no (institution-side) |
| `fundtransferAdvice_dc` | 020 `FTAdviceCreditRequest` / 021 `FTAdviceCreditResponse` | no (institution-side) |
| `fundtransferAdvice_dd` | 022 `FTAdviceDebitRequest` / 023 `FTAdviceDebitResponse` | no (institution-side) |

Section 6 states that NIBSS itself exposes only `nameenquirysingleitem`, `fundtransfersingleitem_dc`, and `txnstatusquerysingleitem`; the other methods are exposed by financial institutions. The simulator also answers them so the same messages can be exercised over SOAP. A client that targets the real NIBSS service must use only the three NIBSS-exposed methods.

### Envelope

SOAP 1.1, `Content-Type: text/xml`. The request matches the NIBSS Postman sample: the body holds `<core:{method}>` in namespace `http://core.nip.nibss/` with one **unqualified** child `request` whose text is the SSM-encrypted NIP request message.

```xml
<soapenv:Envelope xmlns:soapenv="http://schemas.xmlsoap.org/soap/envelope/" xmlns:core="http://core.nip.nibss/">
   <soapenv:Header/>
   <soapenv:Body>
      <core:nameenquirysingleitem>
         <request>848C03...;</request>
      </core:nameenquirysingleitem>
   </soapenv:Body>
</soapenv:Envelope>
```

The response (HTTP `200`, `text/xml; charset=utf-8`) uses the JAX-WS document/literal-wrapped default. Its single unqualified child `return` holds the SSM-encrypted NIP response message:

```xml
<S:Envelope xmlns:S="http://schemas.xmlsoap.org/soap/envelope/">
  <S:Body>
    <ns2:nameenquirysingleitemResponse xmlns:ns2="http://core.nip.nibss/">
      <return>848C03...;</return>
    </ns2:nameenquirysingleitemResponse>
  </S:Body>
</S:Envelope>
```

The response element name is **unverified** (see [Unverified](#unverified)); it is defined once, in `NibssNipSoap.RESPONSE_ELEMENT`.

The decrypted request is processed exactly like the v9.4 XML routes below: same messages, validation, simulated behavior, and response XML. The SOAP request carries nothing but the NIP message: no simulator header, parameter, or element exists.

### WSDL

`GET {path}?wsdl` returns a WSDL 1.1 document/literal-wrapped description of the service at that path: target namespace `http://core.nip.nibss/`, `elementFormDefault="unqualified"`, for each of the seven methods a wrapper element `{method}` with one `request` string and `{method}Response` with one `return` string, one message per element, `soapAction=""`, and `soap:address` set to the URL the client used (host, scheme, and base path included). It is generated by the simulator from the facts above, not copied from NIBSS.

### SOAP faults

The specification does not define how NIBSS answers a request it cannot dispatch or decrypt. The simulator answers with a standard SOAP 1.1 fault, HTTP `500`, `text/xml`:

| Situation | `faultcode` |
|---|---|
| Body is not well-formed XML, contains a DTD, has no SOAP `Body`, or the body holds anything but one operation element | `S:Client` |
| Envelope is not SOAP 1.1 | `S:VersionMismatch` |
| Unknown method or namespace other than `http://core.nip.nibss/` | `S:Client` |
| Missing or empty `request` element | `S:Client` |
| `request` is not an SSM payload for the simulator key | `S:Client` |
| No institution public key is configured, so the answer cannot be encrypted | `S:Server` |

No transaction is recorded in any of these cases. The content type of the request is not checked.

## SSM message security

Derived from `SSMLib` in `SSecurityModule.jar`:

- **Encrypt:** the plaintext is split into consecutive 1024-character substrings. Each substring's UTF-8 bytes are OpenPGP public-key encrypted as a **binary** (not ASCII-armored) message with **no integrity-protection packet** (symmetrically encrypted data packet, tag 9) containing a literal data packet. The simulator uses CAST5 and ZIP compression, the legacy SSM library defaults. Each encrypted chunk is written as **uppercase hexadecimal followed by `;`**, so the output always ends with `;`.
- **Decrypt:** split on `;`, ignore empty tokens, decode each token as hexadecimal (either case), decrypt with the private key, and concatenate. Any symmetric algorithm, compression, or integrity protection supported by Bouncy Castle is accepted.
- **Keys:** RSA-2048 OpenPGP key pairs, exchanged in binary form. Requests to the simulator are encrypted with the **simulator (NIBSS) public key**; responses and inward requests are encrypted with the **institution public key**.

### Keys

| Key | Source |
|---|---|
| Simulator key pair (plays NIBSS) | **Built-in test key pair** (`src/main/resources/nibss-nip/simulator-test-secret-key.asc`), identical on every start, machine, and release: RSA-2048 primary key with an RSA-2048 encryption subkey, user ID `NIBSS NIP Simulator TEST KEY - NOT FOR PRODUCTION`, fingerprint `86114BA1ABFFCA5D322DCCE909AC730FDC684398`. Institutions can download its public key once and keep it in their test configuration. Its private key is public by design: never use it to protect real traffic. To use a different key (for example a shared staging environment), set `NIBSS_NIP_SIMULATOR_PRIVATE_KEY` (Base64 of an armored or binary secret key ring) and `NIBSS_NIP_SIMULATOR_PRIVATE_KEY_PASSPHRASE`. |
| Institution public key | `NIBSS_NIP_CLIENT_PUBLIC_KEY` (Base64 of an armored or binary public key ring) and/or the admin upload below; the latest upload wins until restart. Set the environment variable to avoid uploading after every restart. |

Invalid configured keys fail startup. Key material is never logged; the startup log shows fingerprints only.

| Admin endpoint | Purpose |
|---|---|
| `GET /admin/providers/nibss-nip/keys/simulator-public` | Simulator public key, binary `application/pgp-keys`, `Content-Disposition: attachment; filename="nibss_public.key"` (the file SSM loads as `nibss_public.key`). `?format=armored` returns ASCII armor. |
| `PUT /admin/providers/nibss-nip/keys/client-public` | Body: the institution public key ring, armored text or binary. `204`; an unusable key is rejected with `400` `{"error":"INVALID_KEY","message":...}`. |
| `GET /admin/providers/nibss-nip/keys` | Fingerprint, key IDs, encryption key ID, and user IDs of the simulator key and the institution key (`null` when absent). No key material. |

## Inward flow (simulator plays NIBSS)

Per `FT Credit Implementation in Steps.txt`: NIBSS sends an FT credit to the institution; the institution answers `00` but does not credit yet; about 60 seconds later it sends a TSQ for that `SessionID` to NIBSS (`/NIPWS/NIPTSQInterface`) and credits only if the TSQ answers `00`.

| Admin endpoint | Message sent to the institution |
|---|---|
| `POST /admin/providers/nibss-nip/inward/name-enquiry` | 010 `NESingleRequest` via `nameenquirysingleitem` |
| `POST /admin/providers/nibss-nip/inward/credit` | 012 `FTSingleCreditRequest` via `fundtransfersingleitem_dc` |

Request bodies (JSON):

- name enquiry: `destinationInstitutionCode` (6 digits), `accountNumber`, `channelCode` (default `1`);
- credit: `destinationInstitutionCode`, `beneficiaryAccountName`, `beneficiaryAccountNumber`, `beneficiaryBankVerificationNumber`, `originatorAccountName`, `originatorAccountNumber`, `originatorBankVerificationNumber`, `amount` (required); `channelCode` (default `1`), `nameEnquiryRef`, `beneficiaryKycLevel`, `originatorKycLevel`, `transactionLocation`, `narration`, `paymentReference` (optional, omitted from the message when absent). `Amount` is sent with two decimals.

The simulator generates the `SessionID` in the specification format: characters 1–6 the sender code (`inward.source-institution-code`, default `999999`), 7–18 `yyMMddHHmmss` in West Africa Time, 19–30 a random 12-digit number. It encrypts the message with the institution public key, posts a SOAP 1.1 envelope shaped like the NIBSS sample to `inward.url` with `SOAPAction: "{inward.soap-action}"`, and decrypts the answer with the simulator private key. Institution WSDLs differ, so the operation namespace (`inward.namespace`) and request element (`inward.request-element`) are configurable, and the answer is read from the **first child element** of the operation response element, whatever its name (`return`, `{method}Result`, ...).

Successful admin response (`200`):

```json
{
  "sessionId": "999999251107193000123456789012",
  "method": "fundtransfersingleitem_dc",
  "url": "http://bank.example/NIPInward",
  "requestXml": "<FTSingleCreditRequest>...</FTSingleCreditRequest>",
  "responseXml": "<FTSingleCreditResponse>...</FTSingleCreditResponse>",
  "responseCode": "00",
  "httpStatus": 200,
  "transactionStatus": "SUCCESS",
  "statusQueryResponseCode": "00"
}
```

`transactionStatus` and `statusQueryResponseCode` are present for credits only and describe what the institution's TSQ answers for that `SessionID` right now.

### Recording an inward credit

The credit is recorded under provider `nibss-nip`, reference `SessionID`, operation `inward-fund-transfer-direct-credit`, so the institution's outward TSQ answers it:

| Institution answer | Recorded through | TSQ answers |
|---|---|---|
| `00` | the normal behavior resolution for `inward-fund-transfer-direct-credit` | `success`: `00`; `failure`: `96` (NIBSS did not get or accept the institution's response, so it must not credit); `pending`: `09`, then the profile's final status |
| anything else | recorded as failed | `96` |
| no usable answer (connection, timeout, HTTP error, SOAP fault, undecryptable or unreadable message) | nothing recorded | `25` |

A call without a usable answer returns `502` `{"error":"INWARD_CALL_FAILED","message":...,"sessionId":...,"method":...,"url":...,"requestXml":...,"httpStatus":...}`. Inward calls are refused with `400` `{"error":"INWARD_NOT_CONFIGURED",...}` when the institution public key or `inward.url` is missing; invalid bodies are `400` `VALIDATION_ERROR`.

### Control-plane placement

The NIBSS admin endpoints live in the provider module but are annotated `@ControlPlaneEndpoint`, so they always stay at `/admin/providers/nibss-nip/...` behind `X-Admin-Token`: the provider base path never applies to them, and they stay available when the provider is disabled. Their errors use the admin error shape (`error`, `message`), never NIP messages.

## v9.4 XML routes

| Messages | XML roots | Local route |
|---|---|---|
| 010/011 | `NESingleRequest` / `NESingleResponse` | `POST /nip/v9.4/nameenquirysingle` |
| 012/013 | `FTSingleCreditRequest` / `FTSingleCreditResponse` | `POST /nip/v9.4/fundtransfersingleitem_dc` |
| 014/015 | `FTSingleDebitRequest` / `FTSingleDebitResponse` | `POST /nip/v9.4/fundtransfersingleitem_dd` |
| 016/017 | `TSQuerySingleRequest` / `TSQuerySingleResponse` | `POST /nip/v9.4/txnstatusquerysingleitem` |
| 018/019 | `BalanceEnquiryRequest` / `BalanceEnquiryResponse` | `POST /nip/v9.4/balanceenquiry` |
| 020/021 | `FTAdviceCreditRequest` / `FTAdviceCreditResponse` | `POST /nip/v9.4/fundtransferAdvice_dc` |
| 022/023 | `FTAdviceDebitRequest` / `FTAdviceDebitResponse` | `POST /nip/v9.4/fundtransferAdvice_dd` |

Requests must be `application/xml`; every response is `application/xml` with HTTP `200`. These routes are a local transport without SSM and are not NIBSS production URLs; they require no authentication. Field names and response root names preserve the casing and ordering shown in the specification examples. Narration is limited to 100 characters. With a base path, they are served under it (`/nibss/nip/v9.4/...`) and nowhere else.

## Response codes

| Code | Meaning | Used for |
|---|---|---|
| `00` | Approved or completed successfully | Successful operation; status query of a successful transfer |
| `09` | Request processing in progress | Pending transfer; status query of a pending transfer |
| `25` | Unable to locate record | Status query for a `SessionID` with no transaction |
| `30` | Format error | Missing or invalid elements, unreadable XML, non-XML content type (see [Error rendering](#error-rendering)) |
| `94` | Duplicate transaction | Transfer repeating the `SessionID` of an existing transfer |
| `96` | System malfunction | Failed operation; status query of a failed transfer |

NIP has no response code for a client-side timeout: a simulated timeout returns no response at all, on either transport. NIP has no status-query code for a reversed transaction, so reversal cannot be simulated for this provider.

## Simulated operations

Behavior is selected only through the admin API or configuration (`/admin/overrides`, `/admin/rules`, `/admin/providers/nibss-nip/...`); the reference used by overrides is the NIP `SessionID`. Test-data rules may match the listed request elements, named exactly as in the NIP messages. Both transports share the same operations and state.

| Operation | Message | Kind | Outcomes | Status query reports | Match fields |
|---|---|---|---|---|---|
| `name-enquiry` | 010/011 | stateless | success, failure, timeout | — | `DestinationInstitutionCode`, `ChannelCode`, `AccountNumber` |
| `fund-transfer-direct-credit` | 012/013 | transactional | success, failure, pending, timeout | pending, success, failed | `DestinationInstitutionCode`, `ChannelCode`, `BeneficiaryAccountNumber`, `OriginatorAccountNumber`, `Amount` |
| `fund-transfer-direct-debit` | 014/015 | transactional | success, failure, pending, timeout | pending, success, failed | `DestinationInstitutionCode`, `ChannelCode`, `DebitAccountNumber`, `BeneficiaryAccountNumber`, `MandateReferenceNumber`, `Amount` |
| `balance-enquiry` | 018/019 | stateless | success, failure, timeout | — | `DestinationInstitutionCode`, `ChannelCode`, `TargetAccountNumber` |
| `fund-transfer-advice-direct-credit` | 020/021 | stateless | success, failure, timeout | — | same as `fund-transfer-direct-credit` |
| `fund-transfer-advice-direct-debit` | 022/023 | stateless | success, failure, timeout | — | same as `fund-transfer-direct-debit` |
| `inward-fund-transfer-direct-credit` | 012/013 sent by the simulator | transactional | success, failure, pending | pending, success, failed | same as `fund-transfer-direct-credit` |

`Amount` is matched as its plain decimal text, for example `1000.00`. The inward operation has no timeout outcome because the admin call that drives it is never dropped.

The transaction status query (016/017) is not a simulated operation: it reports the recorded state of a direct-credit, direct-debit, or inward credit by `SessionID` and cannot be assigned a profile.

### Supported profiles

| Profile | Stateless operations | Transfers | Inward credit (TSQ after `00`) |
|---|---|---|---|
| `happy-path`, `delayed-success` | `00` | `00`; query `00` | `00` |
| `failure` | `96` | `96`; query `96` | `96` |
| `pending` | not supported | `09`; query `09`, then `00` | `09`, then `00` |
| `pending-then-failed` | not supported | `09`; query `09`, then `96` | `09`, then `96` |
| `pending-forever` | not supported | `09`; query `09` until the record expires | `09` until the record expires |
| `pending-then-reversed` | not supported | not supported (no reversed code) | not supported |
| `timeout` | no response | no response; query `00` | not supported |
| `timeout-then-failed` | no response | no response; query `96` | not supported |
| `timeout-not-received` | no response | no response; query `25` | not supported |

The admin API rejects a profile an operation cannot express. A timeout holds the request for the profile delay and then closes the connection without sending any bytes.

## Error rendering

Requests whose NIP message cannot be processed are answered with the operation's own response message carrying `ResponseCode` `30`. On the v9.4 routes it is returned as HTTP `200` `application/xml`; over SOAP it is returned SSM-encrypted in a normal SOAP response:

- missing or invalid required elements: request elements that were read are echoed as in a normal response;
- unreadable XML, including any document with a DTD or external entity (rejected by the XML reader; entities are never resolved): only `ResponseCode` is populated;
- v9.4 only: a request that is not `application/xml`: only `ResponseCode` is populated.

The transaction is not recorded in any of these cases. SOAP envelopes that cannot be dispatched or decrypted are answered with SOAP faults (see [SOAP faults](#soap-faults)).

## Unverified

These details are not stated in the supplied material and are implemented as documented assumptions. Confirm them against NIBSS's WSDL (`http://{IP}/NIPWS/NIPInterface?wsdl`) or a captured NIBSS response:

- **Response element `return`.** The SOAP response wraps the encrypted message in `<ns2:{method}Response><return>`, the JAX-WS default; defined once in `NibssNipSoap.RESPONSE_ELEMENT`.
- **soapAction.** Empty for every operation, in the simulator WSDL and for inward calls (`inward.soap-action`). The institution WSDL listed under Sources also uses `soapAction=""`.
- **Fault format.** SOAP 1.1 faults with HTTP `500` for undispatchable, undecryptable, or unanswerable requests, and the fault codes listed above.
- **Inward institution element names.** The operation namespace and request element of the institution's inward service are configurable (defaults `http://core.nip.nibss/` and `request`); the answer is accepted from the first child of the operation response element.
- **WSDL service, port, and binding names** (`{path name}`, `{path name}Port`, `{path name}PortBinding`).

## Limitations and assumptions

- The response-code meanings follow the NIP response-code list. Every failure is reported as `96`; more specific NIP failure codes (for example invalid account or insufficient funds) are not simulated.
- Requests for undefined routes or unsupported HTTP methods are rejected by the simulator before any NIBSS handler is selected and are not answered in NIP form.
- Only one institution public key is held at a time. Uploaded keys and generated simulator keys are lost on restart unless supplied through the environment.
- Not implemented: v9.5 messages 024 through 037 (amount block/unblock, account block/unblock, financial institution list, mandate advice, transaction response acknowledgement).
- All state is in memory, bounded, has a TTL, and is lost on restart.

## Validation and safety

Integration tests cover all implemented message pairs on the v9.4 routes; over SOAP: name enquiry on all three paths, FT credit, TSQ, duplicates, profile failure, format errors for invalid inner messages and external entities, faults for garbage payloads, unknown methods, missing `request`, malformed envelopes, DTDs, SOAP 1.2 envelopes, and a missing institution key, a timeout as a dropped connection, the WSDL of every path, and base-path mounting. Inward tests run against a fake institution web service with throwaway keys: approved credit confirmed by TSQ `00`, inward failure profile (`96`), institution non-`00` (`96`), unreachable institution (`502`, TSQ `25`), name enquiry, missing institution key, and the admin token and `/admin` placement under a base path. SSM unit tests cover round trips, 1024-character chunking, hexadecimal case and terminators, binary packets without integrity protection, tolerant decryption, and passphrase-protected secret keys. No test uses kit keys or other kit material.
